# Architecture decision 0024: Singleplayer on a local Paper server, PvP modules, and shared skeletons

Status: accepted. Implemented 2026-10-31.

## Context

The user asked for four things:

1. If singleplayer is not (nearly) working, run a Paper server (or something better, perhaps Alkaline's own fork)
   as the client-side server, with the EULA accepted by default.
2. More PvP modules, with no restrictions on what they are.
3. A study of the optimization techniques in the popular optimization mods, using their sources.
4. Faster model rendering if there is room: novel approaches, plus any obvious or existing optimizations Alkaline
   could use.

Singleplayer only listed worlds; Play was disabled ("not scheduled: it needs an integrated server",
[implementation waves](../implementation-waves.md)). So task 1 applied.

## Decision: singleplayer runs on a local Paper 1.8.8 server

`IntegratedServer` (`modules/client`) runs the world on **Paper 1.8.8 build 445** in a child JVM on 127.0.0.1, in
offline mode. The client then joins it through the multiplayer path. Protocol 47 is shared by 1.8.8 and 1.8.9.

- **Why Paper, not vanilla or a fork:** the user asked for Paper. 1.8.8-445 (December 2021, after Log4Shell)
  starts on Java 25 with `use-native-transport=false`, the same flag vanilla's 1.8.9 server needs. An Alkaline
  fork would mean maintaining a server. Mojang's server would have kept the save layout as is, but it has none of
  Paper's chunk and tick work.
- **Download:** the jar comes from PaperMC's Fill API, is checked against its SHA-256 (`7ff6d2ce…`), and is cached
  in `~/.alkaline/legacy/server/`. On the first start, Paperclip downloads Mojang's 1.8.8 server jar and patches it.
  Later starts run `cache/patched_1.8.8.jar` directly. Nothing from Paper or Mojang is committed or redistributed.
- **EULA:** `eula.txt` is written with `eula=true` on the player's behalf, as requested.
- **The save stays a vanilla save:**
  - Bukkit keeps the Nether and the End in separate world folders, and on first start it would *move* `DIM-1` and
    `DIM1` out of the save. Instead, the server gets a world container of links: `<id>` links to the save, and
    `<id>_nether/DIM-1` and `<id>_the_end/DIM1` link to the save's own dimension folders.
  - On Windows, a junction (`mklink /J`) replaces the symbolic link when Developer Mode is off. This path is not
    tested yet.
  - The singleplayer player lives in `level.dat`'s `Data.Player`, which a dedicated server ignores. Before the
    start, it is copied to `playerdata/<offline uuid>.dat`; after the server has saved and exited, it is copied
    back. The display name is put back too, because the dedicated server renames the world to its level name.
  - Game mode, difficulty and hardcore come from `level.dat`, since the dedicated server forces its properties
    onto the world. Cheats make the player an operator.
- **Settings that matter for one player on loopback:**
  - `network-compression-threshold=-1`: compression only costs both processes CPU.
  - Anti-xray and timings off.
  - Connection throttle off.
  - The view distance follows the client's render distance.
  - Only the Overworld's spawn chunks stay loaded, as in vanilla.
- **Startup**, measured on this machine (existing flat world, time to "Done"):

  | Launch | Ready |
  | --- | --- |
  | Paperclip jar | 2.28 / 2.31 s |
  | Patched jar directly | 2.17 / 2.16 s |
  | Patched jar + AppCDS (`-XX:+AutoCreateSharedArchive`) | 1.65 / 1.55 s |
  | + no Nether/End spawn preloading | 1.12 / 1.13 s |
  | `-XX:TieredStopAtLevel=1` (dropped) | 2.44 / 2.01 s |

  The child JVM also uses `-XX:+UseCompactObjectHeaders`. A new world spent 5.2 s preparing its spawn area.
- **Menu:**
  - Play opens the selected world.
  - New world creates a default survival world. Its folder name follows vanilla's create-world screen (dashes are
    appended on collisions).
  - While the server starts, the joining card shows its progress ("Preparing spawn area 56%").
  - The pause card's Disconnect becomes Save and quit. Leaving stops and saves the server, then returns to the
    world list.
  - `--world <save folder>` opens a world from the command line, like `--join`.
- **World pictures:** 1.8.9 never writes `icon.png`. A save without one now shows the 64x64 blocks around its
  player, drawn the way a 1.8.9 map item draws them (`ItemMap.updateMapData`): the top block's map color, shading
  by height step and water depth.
  - Only the region files of the needed chunks are read; nothing is written.
  - The block-to-map-color table (`block-map-colors.csv`) was generated by calling the vanilla 1.8.9 client's
    `Block.getMapColor` for every id and metadata.

## Decision: PvP modules

- **New HUD modules** (data from `CombatTracker`):
  - **Reach display:** the eye-to-hitbox distance of the last *landed* hit. A hit counts when the server answers
    the attack with the target's hurt status within a second; hits into hurt-resistance ticks get none.
  - **Combo counter:** landed hits in a row. Your own hurt status ends it, and so do three seconds without a hit.
  - **Target HUD:** the player you are fighting: team-colored name, health from its metadata, worn armor and held
    item, and distance.
  - **Armor status:** worn pieces and the held item, with uses left.
  - **Item counter:** golden apples, pearls, instant health potions, soups and arrows across the inventory.
- **New gameplay modules:**
  - **Freelook:** while the key is held (Left Alt), the camera orbits in third person and the aim stays put.
  - **Hitboxes:** vanilla's F3+B: the box, a red band at the eyes, and a blue look line. Players only, or every
    entity.
  - **Block outline:** vanilla's selection box, which Alkaline did not draw at all until now. On by default, with
    color and thickness options. The box is the union of the block's collision boxes within its cell, so stairs
    outline as a cube and fences one block tall, as in vanilla. Blocks without collision (plants) outline their
    whole cell.
- Lines are camera-facing quads whose width grows with distance, so they keep a constant pixel width
  (`OutlineView`). Vulkan has no portable wide lines.
- Hurt shake and hit color already existed as Video settings, so they did not become modules.

## Study: what the popular optimization mods do

Ranked by Modrinth downloads (2026-10-31). Their sources are in `../reference/repo/`, read-only; no code was taken.

| Mod | Technique | In Alkaline |
| --- | --- | --- |
| Sodium | Chunk meshing; entity cuboids transformed as 8 corners on the CPU, with face culling | GPU-instanced models already go further (geometry uploaded once) |
| EntityCulling | Async ray-cast occlusion of entities and block entities | Not adopted: culling is not the focus ([performance work](0015-renderer-performance-and-vulkan-1-4.md)) |
| FerriteCore | Deduplicated block-state and model data (memory) | Alkaline's block tables are flat arrays already |
| Lithium | Server tick logic | Paper has its own tick work |
| ImmediatelyFast | Batched immediate-mode draws; text, map and HUD fast paths | Everything is batched by design; the HUD is cached between HUD frames |
| ModernFix | Lazy resources and faster startup | Assets and textures already load off the render thread |
| More Culling | Leaves, item frames and sign text | Leaf culling done earlier (decision 0020) |
| Dynamic FPS | Fewer frames when unfocused or hidden | A minimized, hidden or occluded window already stops drawing |
| BadOptimizations | Rebuild the lightmap only when its inputs change; cache the sky color | The lightmap has a dirty flag already |
| Enhanced Block Entities | Chests and signs baked into chunk meshes | Possible later: chests are still instanced models |
| Krypton | Network varints and flush batching | Not measured as a cost |

The useful finding: the obvious wins are in place already. What remained in model rendering is redundant work in
Alkaline's own design, below.

## Decision: shared skeletons in the model renderer

Every armor piece copied the wearer's pose, then resolved and wrote the whole biped skeleton again (7 parts of trig
and matrix products, hidden parts as zero matrices), and so did the emissive pass. A fully armored player cost five
skeletons per frame.

- **Matrices:** `PoseMath.resolveAll` resolves every part. Visibility moves into a 64-bit mask
  (`PoseMath.visibleMask`).
- **Headers:** each instance's record now points at a 16-byte header row: the mask and the first matrix row.
- **Sharing:** when a posed submit has the same parent chain, rotations, pivots and root as the skeleton written just
  before (`SkeletonMatch`, an exact comparison), its header points at those matrices. Nothing is approximated:
  shared rows are the matrices the layer would have resolved itself (`SkeletonMatchTest`).
- **Shaders:** `model.vert` and `model_glint.vert` read the header and collapse hidden parts to the origin, as a zero
  matrix did.
- **Cost:** JMH `SkeletonSharingBenchmark`, one armored player's CPU submit (Intel Core i5-10400F, JDK 25, Linux,
  1 fork, 5 iterations):

  | Path | Time |
  | --- | --- |
  | Separate skeletons | 1278 ± 95 ns |
  | Shared skeleton | 752 ± 54 ns (−41%) |

  The armor's stream writes drop from 4 × 7 matrices (1,344 bytes) to four 16-byte headers.

## Not verified

- **In game:** reach, combo and the Target HUD. The scripted check used a headless second player, which the client
  drew about 4 blocks from where the server had teleported it, so no hit landed. It is unclear whether that is the
  harness or a client bug. Hitboxes, Armor status and Item counter were seen working in game.
- **Not run in game at all:** Freelook, Block outline and the shared-skeleton shaders. The user is testing these.
- **Windows:** junctions, and the server on Windows.
- **Paper's gameplay:** it differs from vanilla in places (Spigot's item merge radius, entity activation ranges);
  none are tuned yet.
